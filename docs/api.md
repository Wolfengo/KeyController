# KeyController local API v1

`kctrl --help` lists the public agent-facing commands. The transport is newline-delimited JSON, with a 64 KiB request limit. `/run/ssh-keys/UID/control.sock` serves queries and unlock requests; `/run/ssh-keys/UID/desktop.sock` serves the widget's metadata, direct revocation/mode actions and native management dialogs. Both check `SO_PEERCRED`; clients verify the server is root and the containing directories are root-owned and not writable by other users. There is no network listener.

Every response includes `api_version`, `state`, `key_id`, `request_id`, `expires_at`, `error_code`. Pending/terminal requests and direct-action responses also include `operation`, such as `unlock`, `sync`, `mode` or `revoke`; it describes the operation, not the transport action. Unused identifiers, expiry and error are JSON null. Unix timestamps are seconds. `lifetime_known` distinguishes a managed unlimited load (`true`, expiry null) from a foreign load (`false`, expiry null). A foreign successful identity mutation conservatively invalidates all recorded lifetimes; the OpenSSH agent still enforces its actual timers.

Request example:

```json
{"api_version":1,"action":"keys.unlock","key":"SHA256:example","interactive":true,"reason":"Continue SSH connection to note"}
```

Accepted response:

```json
{"api_version":1,"state":"pending","operation":"unlock","key_id":"SHA256:example","request_id":"128-bit-random-id","expires_at":null,"error_code":null}
```

`pending` is not access. Exit code **3** is reserved for pending; **0** means a completed query or successful unlock, and **1** means failure, denial, cancellation, expiry or partial completion. `keys.status` can return `locked` with exit 0 because the query succeeded; always examine `state`.

The public socket permits only `capabilities`, `keys.list`, `keys.status`, `keys.unlock`, `requests.status` and `requests.cancel`. This is enforced by the service, not just the CLI: direct calls to `sync`, `encrypt`, `rules.global`, `rules.key`, `settings.global`, `settings.key`, `mode`, `unbind`, `revoke`, `panel.list`, `scan` or `dialog.open` return `forbidden`. Public `requests.status` and `requests.cancel` operate only on unlock requests; management request IDs are hidden and cannot be used on this endpoint. Public key metadata does not expose active management request IDs. Unknown command fields (including passphrase or confirmation fields) are rejected. The CLI never accepts passwords, policy updates, enrollment, or encryption. An exact fingerprint is preferred. An unambiguous filename is accepted. An ambiguous name returns `ambiguous_key`. Symlink aliases resolve to the same identity; different plaintext copies are reported under `unencrypted_copies`.

`capabilities.fingerprint_autostart` is `true`: a bound key with saved fingerprint mode starts scanning when its protected window appears. `interactive_required:true` still requires an unlocked local session and interactive authentication; it does not mean a preliminary button click. Requests remain pending until authentication and agent loading succeed.

Public `capabilities.capabilities` lists the five query/request actions (`keys.list`, `keys.status`, `keys.unlock`, `requests.status`, `requests.cancel`). Its `request_limits` is `{"windows_per_minute":3,"cancel_cooldown_seconds":30,"scope":"unlock_requests"}`. `capabilities` also reports `"revocation":{"automatic":"openssh_lifetime","manual":true,"on_lock":false,"on_sleep":true,"sleep_supported":true}`; `manual:true` describes the desktop UI feature, not permission to invoke revocation through the public socket. `on_sleep` reflects the current user’s configured option (the example is a fresh installation); `sleep_supported` advertises the integration.

Unlock uses the saved per-key method without a second selector in the protected native window. For a bound key in fingerprint mode, scanning starts once the window is exposed, without a separate Unlock click. This applies equally to widget, CLI and AI requests; access still requires fresh successful PAM fingerprint authentication. The window shows the key fingerprint and effective lifetime before scanning, plus **Request via:** the requesting transport executable and any supplied reason. Details retains the full executable/PID, key path and copyable fingerprint. The program name is display metadata, not proof of a manual action or the identity of a higher-level application that invoked the transport. Closing the window cancels the request. In password mode, the SSH-passphrase field is immediately available; Enter or Unlock submits the nonempty passphrase through the private channel. Opening the password window or typing alone does not submit it. Unbound keys always use their SSH passphrase. Binding, encryption and unbinding retain their native confirmation flows. Global and per-key access rules are edited and saved in a native window. Only revocation and changing the preferred unlock method act directly in the widget without a separate window.

The widget shows an immediate submitting state even when its command is queued behind a metadata poll, then retains a bar indicator for a pending request. A 12-second transport watchdog reports an unresponsive RPC without resubmitting unlock. An already known pending request ID is retained after a polling failure so it can still be tracked/cancelled. Neither a timeout nor a progress indication means access has been granted.

Detailed phases are private worker-to-prompt messages, not part of the public/desktop API. The message is `{"state":"progress","phase":"…"}` with a fixed phase name: `fingerprint_starting`, `fingerprint_waiting`, `fingerprint_retry`, `credential_decrypting`, `key_loading`, `passphrase_verifying`, `credential_sealing`, `credential_verifying`, or `file_encrypting`. Sensor readiness is shown only after the recognized PAM request to supply a finger. After PAM success the prompt reports verification success, then loading; it does not keep asking for a finger during TPM/key work. Unknown or stale phases cannot change the captured operation/method or repeat authentication. Terminal results and cancellation stop the animation. No raw PAM message, device name or secret is exported to the widget or CLI.

Unlock states: `pending`, `unlocked`, `cancelled`, `denied`, `expired`, `error`. A loaded key returns immediately without a window or renewed timer. One asynchronous operation per user is active across both endpoints; unlock requests for the same operation/key coalesce, and another operation or key gets `busy`. Unlock windows have a limit of three per rolling minute. Unlock cancellation/denial introduces a 30-second cooldown for that key. All unlock callers, including the panel, share these limits; no executable or manual-action flag bypasses them. Management dialogs have a separate three-per-minute limit and no cancellation cooldown. Cancelling binding, encryption or a settings/management dialog does not consume the unlock quota or delay a subsequent unlock. Metadata scans use the same active-operation slot without consuming a window limit. A request expires after 120 seconds using a monotonic clock; this request deadline excludes suspended time on Linux. The system pre-sleep coordinator cancels pending operations before full sleep, independently of the duration clock or screen-lock notification. Session unavailability cancels a pending prompt when observed. History is bounded to 128 in-memory results and is lost on helper restart.

Stable errors include `api_mismatch`, `helper_unavailable`, `wrong_user`, `wrong_server`, `unsafe_socket_directory`, `forbidden`, `key_not_found`, `ambiguous_key`, `key_unavailable`, `key_not_encrypted`, `interaction_required`, `confirmation_required`, `session_locked_or_unavailable`, `session_locked`, `busy`, `cooldown`, `rate_limited`, `request_not_found`, `request_expired`, `cancelled`, `biometric_denied`, `tpm_unavailable`, `credential_unavailable`, `wrong_passphrase_or_invalid_key`, `unlock_failed`, `agent_unavailable`, `file_conflict`, `partial_commit`, `multiple_hard_links`, `outside_ssh_directory`, `unsafe_key_file`, `unsafe_directory`, `invalid_reason`, `invalid_json`, `invalid_mode`, `not_bound`, `invalid_lifetime`, `settings_durability_unknown`, `settings_changed`, `sleep_in_progress`, `operation_failed`, `session_unavailable`, `ptrace_protection_required`, `invalid_confirmation`, `invalid_passphrase`.

The desktop socket accepts `capabilities`, `panel.list`, `scan`, `mode`, `revoke`, `dialog.open`, `requests.status` and `requests.cancel`. Its status/cancellation actions support both unlock and management requests. `panel.list` includes `ui_language` (`ru` or `en`), `scan_root`, `scan_requires_consent`, `sleep_preparing`, `active_request` and `active_operation` so the widget can show the discovery location and track the current dialog. `scan_root` is desktop-only metadata derived from the key owner’s home directory, not a client-selectable path. `scan_requires_consent` is true until successful discovery records approval; legacy `scanned:true` settings retain prior approval, and later inventory invalidation does not ask again. This is an onboarding flag, not socket authorization. `scan` only refreshes key metadata. The widget requests consent before its first recursive discovery of `~/.ssh`; later refreshes are manual. This UI consent is not a separate authorization boundary on the owner-only socket. `capabilities.direct_actions` lists only `mode` and `revoke`; `dialog_actions` lists `sync`, `encrypt`, `rules.key`, `unbind`, `settings.global` and `settings.key`. Direct `rules.global` is forbidden. `native_confirmation_required:true` applies to `native_confirmation_scope:"dialog.open"`. Desktop `interactive_required:true` likewise describes dialog requests; direct actions do not require an `interactive` flag, and that client-supplied flag never proves human input. Desktop `request_limits` is `{"windows_per_minute":3,"cancel_cooldown_seconds":0,"scope":"desktop_dialogs"}`; direct actions open no windows and consume no window quota.

Direct actions require the owner UID and an available unlocked local session. `mode` and `revoke` return the full current key status at the top level with `operation:"mode"` or `"revoke"`, and `request_id:null`; direct actions never return `pending`. The widget applies the returned access/mode state immediately while retaining its open popup.

```json
{"api_version":1,"action":"mode","key":"SHA256:example","value":{"fingerprint_mode":true}}
{"api_version":1,"action":"revoke","key":"SHA256:example","value":null}
```

`mode` requires an existing biometric binding and an explicit boolean; null, unknown fields and other types are rejected. Retrying the same value is idempotent. It changes only the next preferred method, never loads/revokes the key, renews its timer, changes its rules or removes the binding. It returns `busy` while an asynchronous operation is active. A failed settings write leaves the in-memory preference unchanged.

`revoke` requires a null payload and works even if the original key file is now unavailable. It first cancels and fences a pending unlock of the same key, then removes that identity from the agent; a late loader cannot restore it. A normal selective revoke preserves unrelated identities and operations. A whole-agent fallback also stops and fences unfinished loaders before resetting the agent. Repeated revocation of an already closed key succeeds without a window. Failure is returned as an error rather than optimistic success. Existing SSH connections and the encrypted file/binding are retained.

Policy editors are requested through `dialog.open`, with `interactive:true` and a null nested value. A client can open the editor but cannot choose its starting values or approve it. General settings have no key target; per-key settings require the target key:

```json
{"api_version":1,"action":"dialog.open","interactive":true,"value":{"action":"settings.global","value":null}}
{"api_version":1,"action":"dialog.open","key":"SHA256:example","interactive":true,"value":{"action":"settings.key","value":null}}
```

The service captures the current policy before launching the native window. The general editor offers access duration and sleep revocation; the key editor offers a custom duration or inheritance. A lifetime is an integer from 0 to 31536000; 0 means unlimited. **Save** sends the edited policy through that child's private descriptor; no password or biometric scan is required for saving settings. API callers cannot send this approval through either socket. Cancel or expiry before a successful commit leaves the policy unchanged. A changed captured policy returns `settings_changed` rather than overwriting it. Accepted dialogs return `pending`; a successfully committed policy returns `completed`. Clients follow the request and refresh metadata after completion.

Private worker/prompt metadata for `settings.global` contains `value:{"lifetime_seconds":N,"revoke_on_sleep":boolean}`. For `settings.key` it contains `value:{"inherits":boolean,"lifetime_seconds":N,"global_lifetime_seconds":N}`. The native Save reply uses `mode:"settings"`, empty secret fields, and a `value` object with `lifetime_seconds` plus `revoke_on_sleep` for general settings or `inherits` for key settings. The worker and service both reject invalid field types, unknown fields and out-of-range durations. Inheritance persists as a null per-key policy. This is an internal private-channel contract, not a public approval command.

Settings are cloned before atomic saving. A failure before replacement leaves the live policy unchanged. After replacement, the live policy follows the visible file. If directory syncing then fails, the request reports partial completion with `settings_durability_unknown`; clients refresh metadata to show the applied policy and report that durability after a machine crash is unconfirmed. No automatic rollback or retry occurs. Saving rules never extends an existing agent load or changes a binding or preferred method. Sleep-policy changes apply to the next transition and do not revoke current access immediately.

Other management actions use the same `dialog.open` transport. The nested `value` is null for `sync`, `encrypt` and `unbind`. Legacy `rules.key` remains available with a duration object or null to inherit; its separate native confirmation displays the exact caller-proposed target. The current widget uses `settings.key` instead so policy is edited in the native window itself. `mode`, `revoke` and `rules.global` are not valid `dialog.open` actions.

Binding and encryption require native consent and their password/authentication flow. Unbinding requires native confirmation. The service captures the validated target before opening each window and commits only after that worker's successful, uncancelled result. JSON supplied by a client cannot approve its own dialog. Cancelled or expired rules and unbinding confirmations preserve settings, bindings and loaded access. Encryption can finish partially if cancellation races the atomic file replacement; clients must inspect its terminal result. Another asynchronous operation returns `busy` while a dialog is pending.

The packaged `/usr/lib/ssh-keys/panel-client` is a JSON transport, not a privileged client identity. The peer executable and PID are display metadata, never proof of a manual action, and the reason is untrusted plain text. A same-UID program can connect to `desktop.sock` and invoke direct revocation or mode changes, or open a management dialog. The endpoint split does not establish a human-input boundary; it keeps the public unlock API restricted and requires the private native flow for binding, encryption, all policy changes and unbinding. Direct actions can reduce availability or change the next authentication method. They cannot edit policy, extend an existing load, supply a passphrase, satisfy PAM, decrypt a credential or grant access. There are no executable-path exemptions or caller-supplied trust flags. Secrets travel only through the native prompt's private descriptors, never these JSON endpoints or the widget.

Per-key policy JSON is `{"lifetime_seconds":N}` or null to inherit. A fresh installation has global metadata `{"lifetime_seconds":60,"revoke_on_sleep":true}`. Existing persisted durations and sleep preferences are preserved; a missing legacy sleep field remains false. `0` means unlimited. Per-key null means inherit. The upper lifetime bound is one year. The lifetime is passed to OpenSSH at load time. Changing it does not alter an existing load. Screen locking does not revoke loaded keys. Full sleep revokes the managed agent when the global sleep option is enabled. The old `revoke_on_lock` field is removed from stored settings during migration and is rejected in new policy requests. `mode` changes only the next preferred authentication method.

The privileged sleep coordinator has a separate root-only `sleep.sock` in each helper runtime directory. Neither public nor desktop clients may call `sleep.prepare` or `sleep.resume`. The admin transport requires peer UID 0 and an exact request with only `api_version:1` and one of those actions. A ready acknowledgement includes the operation and boolean `revoke_on_sleep`; prepare acknowledges fenced/reaped workers, not completed agent revocation. The system coordinator performs and verifies that stop separately. The root-owned `/run/ssh-keys-sleep/active` fence also blocks additions in the agent proxy and newly started helpers. Mutating/interactive client requests during preparation return `sleep_in_progress`. Resume refuses while this fence exists, and session notifications cannot clear it. This transport accepts no passwords, key targets or policy changes.

`ui_language` is presentation metadata selected from the system message locale in `/etc/locale.conf` (`LC_MESSAGES` before `LANG`). Russian locales select `ru`; English, C/POSIX, absent/unsupported/unsafe configuration select `en`. It is not a request field and confers no caller trust. The widget accepts only these two values; a prompt receives the same fixed language through its private launch environment. Changing this field does not change API state names, error codes, authentication or policy. User-supplied metadata is displayed as plain text in its original language. GNU gettext's `LANGUAGE` preference list and client environment overrides are not used.
