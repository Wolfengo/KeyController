# KeyController local API v1

`kctrl --help` lists the public agent-facing commands. The transport is newline-delimited JSON, with a 64 KiB request limit. `/run/ssh-keys/UID/control.sock` serves queries and unlock requests; `/run/ssh-keys/UID/desktop.sock` serves the widget's metadata, direct revocation/mode/global-settings actions and native management dialogs. Both check `SO_PEERCRED`; clients verify the server is root and the containing directories are root-owned and not writable by other users. There is no network listener.

Every response includes `api_version`, `state`, `key_id`, `request_id`, `expires_at`, `error_code`. Pending/terminal requests and direct-action responses also include `operation`, such as `unlock`, `sync`, `mode` or `revoke`; it describes the operation, not the transport action. Unused identifiers, expiry and error are JSON null. Unix timestamps are seconds. `lifetime_known` distinguishes a managed unlimited load (`true`, expiry null) from a foreign load (`false`, expiry null). A foreign successful identity mutation conservatively invalidates all recorded lifetimes; the OpenSSH agent still enforces its actual timers.

Request example:

```json
{"api_version":1,"action":"keys.unlock","key":"SHA256:example","interactive":true,"reason":"Continue SSH connection to note"}
```

Accepted response:

```json
{"api_version":1,"state":"pending","operation":"unlock","key_id":"SHA256:example","request_id":"128-bit-random-id","expires_at":null,"error_code":null}
```

`pending` is not access. Exit code **3** is reserved for pending; **0** means a completed query or successful unlock, and **1** means failure, denial, cancellation, expiry or partial completion. `keys.status` can return `locked` with exit 0 because the query succeeded; always examine `state`.

The public socket permits only `capabilities`, `keys.list`, `keys.status`, `keys.unlock`, `requests.status` and `requests.cancel`. This is enforced by the service, not just the CLI: direct calls to `sync`, `encrypt`, `rules.global`, `rules.key`, `mode`, `unbind`, `revoke`, `panel.list`, `scan` or `dialog.open` return `forbidden`. Public `requests.status` and `requests.cancel` operate only on unlock requests; management request IDs are hidden and cannot be used on this endpoint. Public key metadata does not expose active management request IDs. Unknown command fields (including passphrase or confirmation fields) are rejected. The CLI never accepts passwords, policy updates, enrollment, or encryption. An exact fingerprint is preferred. An unambiguous filename is accepted. An ambiguous name returns `ambiguous_key`. Symlink aliases resolve to the same identity; different plaintext copies are reported under `unencrypted_copies`.

`capabilities.fingerprint_autostart` is `true`: a bound key with saved fingerprint mode starts scanning when its protected window appears. `interactive_required:true` still requires an unlocked local session and interactive authentication; it does not mean a preliminary button click. Requests remain pending until authentication and agent loading succeed.

Public `capabilities.capabilities` lists the five query/request actions (`keys.list`, `keys.status`, `keys.unlock`, `requests.status`, `requests.cancel`). Its `request_limits` is `{"windows_per_minute":3,"cancel_cooldown_seconds":30,"scope":"unlock_requests"}`. `capabilities` also reports `"revocation":{"automatic":"openssh_lifetime","manual":true,"on_lock":false,"on_sleep":false,"sleep_supported":true}`; `manual:true` describes the desktop UI feature, not permission to invoke revocation through the public socket. `on_sleep` reflects the current user’s configured option; `sleep_supported` advertises the integration.

Unlock uses the saved per-key method without a second selector in the protected native window. For a bound key in fingerprint mode, scanning starts once the window is exposed, without a separate Unlock click. This applies equally to widget, CLI and AI requests; access still requires fresh successful PAM fingerprint authentication. The window shows the requesting program and any supplied reason; full executable/PID, fingerprint, key path and lifetime are available in Details. Closing the window cancels the request. In password mode, the SSH-passphrase field is immediately available; Enter or Unlock submits the nonempty passphrase through the private channel. Opening the password window or typing alone does not submit it. Unbound keys always use their SSH passphrase. Binding, encryption, per-key duration changes and unbinding retain their native confirmation flows. Revocation, changing the preferred unlock method and saving global settings act directly in the widget without a separate window.

The widget shows an immediate submitting state even when its command is queued behind a metadata poll, then retains a bar indicator for a pending request. A 12-second transport watchdog reports an unresponsive RPC without resubmitting unlock. An already known pending request ID is retained after a polling failure so it can still be tracked/cancelled. Neither a timeout nor a progress indication means access has been granted.

Detailed phases are private worker-to-prompt messages, not part of the public/desktop API. The message is `{"state":"progress","phase":"…"}` with a fixed phase name: `fingerprint_starting`, `fingerprint_waiting`, `fingerprint_retry`, `credential_decrypting`, `key_loading`, `passphrase_verifying`, `credential_sealing`, `credential_verifying`, or `file_encrypting`. Sensor readiness is shown only after the recognized PAM request to supply a finger. After PAM success the prompt reports verification success, then loading; it does not keep asking for a finger during TPM/key work. Unknown or stale phases cannot change the captured operation/method or repeat authentication. Terminal results and cancellation stop the animation. No raw PAM message, device name or secret is exported to the widget or CLI.

Unlock states: `pending`, `unlocked`, `cancelled`, `denied`, `expired`, `error`. A loaded key returns immediately without a window or renewed timer. One asynchronous operation per user is active across both endpoints; unlock requests for the same operation/key coalesce, and another operation or key gets `busy`. Unlock windows have a limit of three per rolling minute. Unlock cancellation/denial introduces a 30-second cooldown for that key. All unlock callers, including the panel, share these limits; no executable or manual-action flag bypasses them. Management dialogs have a separate three-per-minute limit and no cancellation cooldown. Cancelling binding, encryption or a settings/management dialog does not consume the unlock quota or delay a subsequent unlock. Metadata scans use the same active-operation slot without consuming a window limit. A request expires after 120 seconds using a monotonic clock; this request deadline excludes suspended time on Linux. The system pre-sleep coordinator cancels pending operations before full sleep, independently of the duration clock or screen-lock notification. Session unavailability cancels a pending prompt when observed. History is bounded to 128 in-memory results and is lost on helper restart.

Stable errors include `api_mismatch`, `helper_unavailable`, `wrong_user`, `wrong_server`, `unsafe_socket_directory`, `forbidden`, `key_not_found`, `ambiguous_key`, `key_unavailable`, `key_not_encrypted`, `interaction_required`, `confirmation_required`, `session_locked_or_unavailable`, `session_locked`, `busy`, `cooldown`, `rate_limited`, `request_not_found`, `request_expired`, `cancelled`, `biometric_denied`, `tpm_unavailable`, `credential_unavailable`, `wrong_passphrase_or_invalid_key`, `unlock_failed`, `agent_unavailable`, `file_conflict`, `partial_commit`, `multiple_hard_links`, `outside_ssh_directory`, `unsafe_key_file`, `unsafe_directory`, `invalid_reason`, `invalid_json`, `invalid_mode`, `not_bound`, `invalid_lifetime`, `settings_durability_unknown`, `sleep_in_progress`, `operation_failed`, `session_unavailable`, `ptrace_protection_required`, `invalid_confirmation`, `invalid_passphrase`.

The desktop socket accepts `capabilities`, `panel.list`, `scan`, `mode`, `revoke`, `rules.global`, `dialog.open`, `requests.status` and `requests.cancel`. Its status/cancellation actions support both unlock and management requests. `panel.list` includes `ui_language` (`ru` or `en`), `sleep_preparing`, `active_request` and `active_operation` so the widget can track the current dialog. `scan` only refreshes key metadata. `capabilities.direct_actions` lists `mode`, `revoke` and `rules.global`; `dialog_actions` lists only `sync`, `encrypt`, `rules.key` and `unbind`. `native_confirmation_required:true` applies to `native_confirmation_scope:"dialog.open"`. Desktop `interactive_required:true` likewise describes dialog requests; direct actions do not require an `interactive` flag, and that client-supplied flag never proves human input. Desktop `request_limits` is `{"windows_per_minute":3,"cancel_cooldown_seconds":0,"scope":"desktop_dialogs"}`; direct actions open no windows and consume no window quota.

Direct actions require the owner UID and an available unlocked local session. `mode` and `revoke` return the full current key status at the top level with `operation:"mode"` or `"revoke"`, and `request_id:null`; direct actions never return `pending`. The widget applies the returned access/mode state immediately while retaining its open popup.

```json
{"api_version":1,"action":"mode","key":"SHA256:example","value":{"fingerprint_mode":true}}
{"api_version":1,"action":"revoke","key":"SHA256:example","value":null}
```

`mode` requires an existing biometric binding and an explicit boolean; null, unknown fields and other types are rejected. Retrying the same value is idempotent. It changes only the next preferred method, never loads/revokes the key, renews its timer, changes its rules or removes the binding. It returns `busy` while an asynchronous operation is active. A failed settings write leaves the in-memory preference unchanged.

`revoke` requires a null payload and works even if the original key file is now unavailable. It first cancels and fences a pending unlock of the same key, then removes that identity from the agent; a late loader cannot restore it. A normal selective revoke preserves unrelated identities and operations. A whole-agent fallback also stops and fences unfinished loaders before resetting the agent. Repeated revocation of an already closed key succeeds without a window. Failure is returned as an error rather than optimistic success. Existing SSH connections and the encrypted file/binding are retained.

`rules.global` accepts `{"lifetime_seconds":N,"revoke_on_sleep":true}`, with an integer from 0 to 31536000; 0 means unlimited. `revoke_on_sleep` is a boolean applying to the whole managed agent. Legacy duration-only requests preserve the saved sleep option. Explicit null/nonboolean values and unknown fields are rejected. The command has no key or request target. Null/missing payloads, extra policy fields, out-of-range values and non-null key/request IDs are rejected. An active asynchronous operation returns `busy`. Settings are cloned before saving. A failure before atomic replacement leaves the live policy unchanged. Once replacement succeeds, the service publishes the policy that is visible on disk. If syncing the containing directory then fails, it returns `state:"partial"`, `error_code:"settings_durability_unknown"` and the applied `global_rules`; durability after a machine crash is unconfirmed. It never silently restores the old policy. The action does not contact the agent or change current expiry, custom per-key rules, binding or preferred method. Sleep-policy changes apply to the next transition and do not revoke access immediately. Repeating the same value is idempotent and uses no window quota.

```json
{"api_version":1,"action":"rules.global","value":{"lifetime_seconds":900,"revoke_on_sleep":true}}
```

Success returns `{"api_version":1,"state":"ready","operation":"rules.global","key_id":null,"request_id":null,"expires_at":null,"error_code":null,"global_rules":{"lifetime_seconds":900,"revoke_on_sleep":true}}`. The widget retains its popup, applies the returned policy to inheriting rows and closes the settings form after success. A failed or malformed reply or a transport timeout keeps the draft visible; the widget never automatically retries the change. The specific `partial`/`settings_durability_unknown` response updates the displayed effective rules while retaining the draft and showing the durability warning. It does not claim a fully successful save.

Management actions are requested through `dialog.open`, with `interactive:true`, the target key and a nested action/value. For example, a per-key duration change is:

```json
{"api_version":1,"action":"dialog.open","key":"SHA256:example","interactive":true,"value":{"action":"rules.key","value":{"lifetime_seconds":900}}}
```

The nested `value` is null for `sync`, `encrypt` and `unbind`. `rules.key` accepts null to inherit global rules. `mode`, `revoke` and `rules.global` are not valid `dialog.open` actions. Accepted dialogs return `pending`; opening a dialog does not authorize a change. Per-key rules and unbinding require separate native confirmation. Binding and encryption require native consent and their password/authentication flow. The service captures the validated target before opening the window and commits only after that worker's successful, uncancelled confirmation. JSON supplied by a client cannot approve its own dialog. Cancelled or expired rules and unbinding confirmations preserve settings, bindings and loaded access. Encryption can finish partially if cancellation races the atomic file replacement; clients must inspect its terminal result. Another asynchronous operation returns `busy` while a dialog is pending. Clients refresh metadata after completion. Existing loaded-key lifetimes are never extended by a rules or mode change.

The packaged `/usr/lib/ssh-keys/panel-client` is a JSON transport, not a privileged client identity. The peer executable and PID are display metadata, never proof of a manual action, and the reason is untrusted plain text. A same-UID program can connect to `desktop.sock` and invoke direct revocation, mode changes or global settings changes, or open a management dialog. The endpoint split does not establish a human-input boundary; it keeps the public unlock API restricted and requires private native confirmation for binding, encryption, per-key rules and unbinding. Direct actions can reduce availability, change the next authentication method or increase the duration of future authenticated loads of inheriting keys, including to unlimited, or enable/disable sleep revocation. They cannot extend an existing load, supply a passphrase, satisfy PAM, decrypt a credential or grant access. There are no executable-path exemptions or caller-supplied trust flags. Secrets travel only through the native prompt's private descriptors, never these JSON endpoints or the widget.

Per-key policy JSON is `{"lifetime_seconds":0}`. Global metadata is `{"lifetime_seconds":0,"revoke_on_sleep":false}`; absent stored sleep settings default to false. `0` means unlimited. Per-key null means inherit. The upper lifetime bound is one year. The lifetime is passed to OpenSSH at load time. Changing it does not alter an existing load. Screen locking does not revoke loaded keys. Full sleep revokes the managed agent when the global sleep option is enabled. The old `revoke_on_lock` field is removed from stored settings during migration and is rejected in new policy requests. `mode` changes only the next preferred authentication method.

The privileged sleep coordinator has a separate root-only `sleep.sock` in each helper runtime directory. Neither public nor desktop clients may call `sleep.prepare` or `sleep.resume`. The admin transport requires peer UID 0 and an exact request with only `api_version:1` and one of those actions. A ready acknowledgement includes the operation and boolean `revoke_on_sleep`; prepare acknowledges fenced/reaped workers, not completed agent revocation. The system coordinator performs and verifies that stop separately. The root-owned `/run/ssh-keys-sleep/active` fence also blocks additions in the agent proxy and newly started helpers. Mutating/interactive client requests during preparation return `sleep_in_progress`. Resume refuses while this fence exists, and session notifications cannot clear it. This transport accepts no passwords, key targets or policy changes.

`ui_language` is presentation metadata selected from the system message locale in `/etc/locale.conf` (`LC_MESSAGES` before `LANG`). Russian locales select `ru`; English, C/POSIX, absent/unsupported/unsafe configuration select `en`. It is not a request field and confers no caller trust. The widget accepts only these two values; a prompt receives the same fixed language through its private launch environment. Changing this field does not change API state names, error codes, authentication or policy. User-supplied metadata is displayed as plain text in its original language. GNU gettext's `LANGUAGE` preference list and client environment overrides are not used.
